Anvil, the host service

Anvil is the only component that holds Docker rights. Consoles ask it for containers; it decides whether they may have them. One instance per host serves every console on that host, and it is deliberately blind to games.

Why it exists

A console is a web application people log into. Giving one the Docker socket means a bug in it is a bug with root on your host. Anvil takes that surface and reduces it to a narrow API: create a container from an allowed image, list them, recreate one, destroy one. It cannot run arbitrary images, cannot mount arbitrary paths, and cannot tell you anything about another console's servers.

Registering your consoles

Each console gets its own entry: an id, a token, a data root, and the environment namespace it is allowed to read back when adopting. Supply it as JSON, inline or from a file — the file wins, and is the better habit for secrets.

ANVIL_CLIENTS_FILE → clients.json
[
  {
    "id": "palcon",
    "token": "<long random string>",
    "dataRoot": "/mnt/tank/apps/palcon-servers",
    "envPrefix": "PALAGENT_",
    "imagePrefixes": ["ghcr.io/safwyls/palagent"]
  },
  {
    "id": "wildskeeper",
    "token": "<long random string>",
    "dataRoot": "/mnt/tank/apps/dragonwilds-servers",
    "envPrefix": "WKAGENT_"
  },
  {
    "id": "flametender",
    "token": "<long random string>",
    "dataRoot": "/mnt/tank/apps/enshrouded-servers",
    "envPrefix": "FLAMEAGENT_"
  }
]

envPrefix is not optional in practice. Adoption returns a container's environment so a console can recover its agent token and passwords, and Anvil filters that to the registered namespace. A client registered without a prefix gets no environment back at all, so adoption produces a server row with no token — which fails with a message telling you exactly this.

The image allowlist

Anvil will only run images whose reference starts with an allowed prefix. A console's own imagePrefixes wins; otherwise the service-wide ANVIL_ALLOWED_IMAGE_PREFIXES applies; otherwise the default, ghcr.io/safwyls/, which already covers every agent image here.

The allowlist does double duty: it also decides which unlabelled containers a console may discover and adopt.

Data roots — and the mount that must exist

Every server's data directory is <that console's dataRoot>/<slug>. The host side is never the caller's choice, which is what stops a console from asking Anvil to mount anything it likes.

Every data root must be mounted into the Anvil container, at the same path it is registered as. Anvil creates and chowns those directories itself. If the path is not mounted, it creates them inside its own filesystem instead, Docker then creates the real directory on the host as root, and the agent container — running as an unprivileged user — cannot write to it.

Nothing complains at the time. SteamCMD exits successfully having installed nothing, and the only symptom is a server that will not start, insisting the game is not installed. See Troubleshooting.

Discovery and adoption

A console can find servers it does not have rows for — after a database loss, or servers you deployed by hand before setting the console up. Anvil offers a container to a console when either:

  • the container carries that console's ownership label, including the legacy per-console labels from before Anvil existed; or
  • it carries no ownership label at all and its image falls under that console's allowlist.

Adopting recovers the agent token, admin password, server name and published ports, so a recovered server needs nothing typed in. Containers belonging to another console are refused with a message saying so, never silently hidden.

Destroying a server

Removing a container never removes its data directory. Unmaking a container is not consent to delete what it was holding — Anvil reports the directory path back so you know what survived and where.

Anvil can only recreate or destroy containers it created. One deployed by hand — a TrueNAS app, your own compose file — is adoptable and readable, but managing its lifecycle stays with whatever deployed it. Two orchestrators fighting over one container helps nobody.

Running it

docker-compose.yml — anvil
services:
  anvil:
    image: ghcr.io/safwyls/anvil:latest
    ports: ["8820:8820"]        # reachable by consoles only
    environment:
      ANVIL_CLIENTS_FILE: /config/clients.json
      ANVIL_PUBLIC_HOST: 192.168.1.9   # how players reach this box
      ANVIL_DEFAULT_RUN_AS: "568:568"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./clients.json:/config/clients.json:ro
      # Every dataRoot, at the path it is registered as. Not optional.
      - /mnt/tank/apps/palcon-servers:/mnt/tank/apps/palcon-servers
      - /mnt/tank/apps/dragonwilds-servers:/mnt/tank/apps/dragonwilds-servers
      - /mnt/tank/apps/enshrouded-servers:/mnt/tank/apps/enshrouded-servers
    restart: unless-stopped

Then point each console at it with ANVIL_URL and that console's ANVIL_TOKEN. The Raise-a-server wizard appears once the console can reach it.
