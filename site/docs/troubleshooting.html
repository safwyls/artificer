Troubleshooting

Each entry below is a real symptom with one dominant cause. Start with the message you actually saw rather than the behaviour you expected.

"Game is not installed — run an update first"

The agent looked for the game in its install directory and did not find it. If an install already appeared to succeed, the cause is almost always a data directory the container cannot write.

SteamCMD does not fail loudly here: it exits successfully having written nothing, so the job is recorded as done and only the refusal to start reveals the problem. Two tells confirm it — the install job finishing far too fast for a multi-gigabyte download, and an empty install directory:

shell
docker exec <agent-container> sh -c 'ls -la "$PALAGENT_INSTALL_DIR"'
docker inspect <agent-container> --format '{{.Config.User}}'

If the directory is owned by root while the container runs as something else, that is it. Fix the ownership and run Update again:

shell
sudo chown -R 568:568 <dataRoot>/<slug>

Then fix the cause so new servers do not repeat it: mount every data root into the Ilmari container at the path it is registered as. See Ilmari.

Newer agents catch this earlier — health reports the install directory as unusable rather than merely present, and an install that reports success without producing the game says so.

The console answers 502

Two different things wear this number, and they are told apart by what the body contains.

  • A JSON error with a message — the console reached the agent and is relaying its failure. The message is the diagnosis; read it literally.
  • A Cloudflare or proxy error page — nothing reached the console at all. Check the console container is running and that your tunnel or proxy still points at it.

Nothing appears in the adopt list

Discovery only offers containers a console may claim. Work down this list:

  • The container's image must fall under that console's allowlist, or the container must carry its ownership label.
  • The console must be able to reach Ilmari at all — without ILMARI_URL the whole wizard is absent.
  • Containers already registered are deliberately excluded; they are in the rail already.

Adoption fails with no agent token

Ilmari returns a container's environment filtered to the console's registered namespace, so a client entry without envPrefix gets nothing back and adoption cannot recover the token. Add the prefix to that entry in ILMARI_CLIENTS and adopt again.

If instead the refusal names the agent port, the container does not publish 8811 and there is no address to reach its agent on. Republish it, or add the server by hand.

A server will not start after provisioning

  • Port already in use — another container or the host itself holds it. The wizard avoids collisions it can see, but not services outside Docker.
  • Out of disk — the agent reports free space on the install directory in its health; the server card shows it.
  • Dragonwilds without an owner id — the game refuses to start with no owner. The agent logs the reason instead of leaving a silent failure.

The power card names the wrong agent

It shows whatever the agent reports itself as. If a Dragonwilds server says flameagent, that container is running the wrong image — check the image reference on the stack.

Cloudflare Access signs in the wrong account

An existing session always wins over a fresh SSO attempt, by design. Log out first — the console ends both its own session and the Access one, which matters on a shared machine.

If a manifest request is blocked by Access, the page needs crossorigin="use-credentials" on its manifest link; current builds have it.

Where to look

QuestionWhere
Did the console reach the agent?Console container logs.
Did the install run, and what did SteamCMD say?The Update log on the server card, or the agent's container logs.
Why did the game exit?The game log on the server card.
Why was a container refused?Ilmari's container logs.
