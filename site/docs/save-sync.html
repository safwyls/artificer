Shared world saves

Some games have no dedicated server worth running — the world lives in one player's save folder, and whoever hosts is whoever has the newest copy. Passing that world around a group by hand ends the same way every time: two people play the same evening, and one of them loses it. Reliquary holds the world instead, and hands it to one player at a time.

One holder at a time

The model is a library book, not a sync folder. There is no merge, because two divergent saves of the same world cannot be merged by anything that does not understand the game.

  • Check out — you take the world. Nobody else can, and your companion installs the current version into your save folder.
  • Play. Mid-session checkpoints upload quietly as crash insurance.
  • Check in — your save becomes the new version and the world is free again.
  • Claim next — if someone else holds it, you queue. The moment they check in, your companion fetches it without you doing anything.

Every check-in is kept as a version, so a world can be rolled back to any of the last N. A hold has a lease; past it, the world becomes claimable by someone else rather than stuck forever behind whoever forgot to check in.

A late check-in is never thrown away. If someone takes over an expired hold and the original holder then checks in, their version is stored and flagged as a conflict instead of overwriting anything — recoverable, just not automatically the truth.

The two pieces

What it isWhere it runs
reliquaryThe service. Holds the worlds, the versions, the custody ledger, the accounts and everyone's tokens. Deliberately game-blind — it never installs a game or talks to one.Your server, one container.
Artificer CompanionA single Windows executable. Finds installed games, links their save folders to worlds, and moves the saves.Each player's gaming machine.

Reliquary is independent of the three consoles. You can run it for games Artificer has no console for at all — it only ever sees a folder of files.

Deploying reliquary

compose.yaml
services:
  reliquary:
    image: ghcr.io/safwyls/reliquary:latest
    restart: unless-stopped
    # :latest tracks main, so an update is a re-pull.
    pull_policy: always
    ports:
      - "8830:8080"
    environment:
      # openssl rand -hex 32 — signs sessions; keep it stable.
      JWT_SECRET: "CHANGE-ME"
      # openssl rand -hex 16 — EXACTLY 32 characters. Encrypts stored tokens.
      ENCRYPTION_KEY: "CHANGE-ME-32-chars-x"
      # The bootstrap admin, created only while the users table is empty.
      ADMIN_USERNAME: "admin"
      ADMIN_PASSWORD: "CHANGE-ME"
      # Behind TLS? Mark session cookies Secure.
      # COOKIE_SECURE: "true"
    volumes:
      - /srv/reliquary:/data

Version archives live under /data as ordinary tar files (savesync/<world>/<version>.tar), with the SQLite database beside them. Give that directory the same snapshot and backup care as any world data.

The container needs no Docker rights and talks to no game. It does not belong on the same trust footing as Anvil — it is closer to a file server that happens to know whose turn it is.

Getting a player set up

  1. Give them an account with the world custody grant. Without it an account can see worlds and download a version, and nothing else — no companion token, no checking out. New accounts made in the Users panel get it; existing ones can be granted it there any time.
  2. They sign in and copy their personal sync token from the Your companion panel. The same panel hands out the executable.
  3. They run the companion — no installer, no service. It opens a page on 127.0.0.1:8377 and sits in the tray. Paste the service URL and token, and nothing leaves the machine until both are set.
  4. They link a game. The companion shows installed games as a shelf of covers; clicking one asks where its save folder is and which world it belongs to — creating the world, and seeding it with the current save, in the same step if this is the first player.

Signing in through Cloudflare Access grants custody automatically, because the Access policy already names exactly the people meant to hold worlds. Set ACCESS_GRANT_CUSTODY=0 to grant each account by hand instead.

Finding the save folder

The companion never syncs a folder the player has not confirmed. It offers candidates, strongest first:

  1. A catalogue of known save locations — the community-maintained Ludusavi manifest, around 13,000 games. Reliquary fetches it weekly so no player's machine pulls 17 MB of it, and sends back path templates the companion expands locally.
  2. Steam Cloud — userdata/<account>/<appid>/remote, keyed by the app id from the game's own manifest.
  3. A name search across Saved Games, %LOCALAPPDATA%, %APPDATA% and Documents\My Games.

Within that order, a folder with files in it outranks an empty one. Anything at all can also be picked by browsing, or typed by hand, and every candidate says where it came from.

Joining a world whose folder has a scrambled name

Unreal games routinely name a save folder with an id generated once and never renameable — K2hAc0p_LH74aymwOemkgg. Everyone playing that world shares it, nobody can retype it, and the game will not create it until it has saved there. Without help, the second player either has to be told the exact string and make the folder by hand, or link their entire SaveGames and sync every save they own.

So a world remembers its own folder name. The player creating it has their chosen folder split into the part that differs per machine and the part that does not, and is shown where the line falls before anything is recorded. Everyone who joins later picks only their own save folder for that game, and their companion creates the world's folder underneath it.

If a game turns out to use that folder to identify the player rather than the world, recreating the first player's name on a second machine may produce a folder that game ignores. The world's folder name is a default, not a mandate — link by hand to a different one if you hit a game that behaves that way.

When the holder goes to bed still holding it

Nothing can reach into a companion — it runs on someone's home machine behind a router — so an admin leaves a request, and that player's companion picks it up on its next poll and answers it. Two verbs, and the difference matters:

Ask forWhat happensUse when
Check inTheir current save is uploaded, becomes the new version, and the world is released.They are away and somebody else wants to play.
CheckpointTheir current save is uploaded. They keep the world.You want a copy of an in-progress session.

Ask for a check-in, not a checkpoint, when you want to take the world over. Checkpoints never move the world's current version by design, so releasing after one would hand the next player a save from before that session started.

A machine that is asleep simply has not answered yet; the request stands until it wakes, and the page says how long it has been waiting. Force release still exists and still means what it says: take the world back, and lose whatever the holder never sent.

Worlds a dedicated server can also hold

Where a game does have a dedicated server — one raised by a console, with its sidecar agent — a world can name that agent and be handed to it. Host on dedicated server pushes the current version into the server's save directory; Take back from server pulls it out and makes it the new version. The server becomes just another holder in the same ledger, so the rule stays one holder at a time whether that holder is a person or a machine.

Behind Cloudflare Access

The companion authenticates with a token in the URL, on purpose: it has no browser to complete a login with. Anything that puts its own login page in front of the service therefore breaks every push — Access answers with HTML and an HTTP 200, and the companion names the interceptor rather than pretending the upload worked.

Fix it with either a bypass or service-auth policy for /api/public/*, or a direct LAN address for players inside the network.

What it is not

  • Not a merge tool. Two people cannot play the same world at once and have it work out. The lock is the feature.
  • Not a live sync. Saves move at checkout and check-in, plus checkpoints — not continuously, because a half-written save is worse than a slightly old one.
  • Not a general backup. It keeps the last N versions of a world you deliberately linked, which is a different job from backing up a disk.
  • Not game-aware. Verification is structural — a well-formed, non-empty, size-bounded bundle. It cannot tell you a save is corrupt, only that it is a save.
