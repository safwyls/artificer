Migrate an existing server

You already have a server with a world people care about. Most of them are running straight on a machine — a folder from SteamCMD, started by a script, a service or by hand — and that is the case this guide leads with. Nothing here deletes a world, and every route can be rolled back, but take a snapshot first anyway.

Which route is yours

How the server runs todayRoute
Directly on a machine — a SteamCMD install you start yourself, or as a systemd unit or Windows service1 — From a bare-metal server
In a container running one of our agent images (palagent, wkagent, flameagent)2 — Adopt it
In some other container or compose setup3 — From another container setup
Under an older console with a provisioner-mode agent4 — Retire the legacy provisioner

Before you start

Collect four facts. Two of them decide whether the migration works at all.

  • Where the world is. The directory holding the save files — see the per-game table below.
  • Which ports it publishes. Reuse them and nobody has to re-add your server.
  • The admin password, from the game's own config file.
  • Which user owns the files, if you are on Linux.

Then copy the world somewhere safe. cp -a, a ZFS snapshot, a zip — whatever is quick. Stop the server first so you are not copying a save mid-write.

Route 1 — From a bare-metal server

Your game server is a directory on a machine. There are two ways in, and the first does not disturb the running server at all — you can do it this afternoon and decide about the second later.

1a. Leave the server where it is, point a console at it

The console runs alongside the game on the same machine and reads its files directly. No agent, no re-install, and the game keeps running the whole time.

You getYou don't
Moderation — kick, ban, unban, broadcastStarting and stopping the process itself, until you either add a supervisor (below) or move to 1b
Save reading — pals, guilds, inventories, storage, world metadata
The settings editor for the game's own config file
Scheduled backups, players, metrics, alerts, in-game shutdown with a countdown

The console is distributed as a container image, so this assumes Docker on that machine. (If you would rather not run Docker at all, the console is a single Go binary and builds from source with go build ./cmd/palcon — the same environment variables apply.)

docker-compose.yml — console beside a bare-metal Palworld server
services:
  palcon:
    image: ghcr.io/safwyls/palcon:latest
    ports: ["8080:8080"]
    environment:
      DATA_DIR: /data
      JWT_SECRET: <openssl rand -hex 32>
      ENCRYPTION_KEY: <openssl rand -hex 16>
      ADMIN_USERNAME: admin
      ADMIN_PASSWORD: <first-login password>
    volumes:
      - ./data:/data
      # Your existing install. The world is read-only — the console never
      # writes a save. The config directory is read-write, because the
      # settings editor edits the file in place.
      - /home/you/palworld/Pal/Saved/SaveGames/0/<world-id>:/saves/main:ro
      - /home/you/palworld/Pal/Saved/Config/LinuxServer:/config/main
    # Lets the container reach the game on the host as host.docker.internal.
    extra_hosts:
      - "host.docker.internal:host-gateway"
    restart: unless-stopped

Then add the server by hand — + → Add an existing server by hand — with:

FieldValue
Hosthost.docker.internal, or the machine's LAN IP
REST / RCON portsWhatever the game is configured for — 8212 and 25575 by default
Admin passwordThe one in your config file
Save path/saves/main — the path inside the console container
Config path/config/main

Paths are what the console sees, not what your shell sees. If a save-backed view says the path is missing, it is nearly always the host side of that bind mount pointing somewhere slightly different.

Palworld needs its management interfaces on for any of the command features to work. In PalWorldSettings.ini:

PalWorldSettings.ini
RESTAPIEnabled=True
RESTAPIPort=8212
RCONEnabled=True
RCONPort=25575
AdminPassword=<something>

Restart the game once for those to take effect. Without REST the console falls back to RCON automatically, but metrics and the in-game shutdown countdown stay unavailable, because RCON has no equivalent commands.

Getting a working restart button without an agent

The console cannot start a process it does not supervise — but it can ask the game to shut itself down, and something else can bring it back. Run the game as a service that restarts on exit and the console's shutdown becomes a restart:

/etc/systemd/system/palworld.service
[Unit]
Description=Palworld dedicated server
After=network-online.target

[Service]
User=palworld
WorkingDirectory=/home/palworld/palworld
ExecStart=/home/palworld/palworld/PalServer.sh -useperfthreads -NoAsyncLoadingThread -UseMultithreadForDS
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target

With Restart=always, an in-game shutdown from the console — including a scheduled restart with player warnings — comes back on its own about ten seconds later. On Windows the same trick works with a service wrapper such as NSSM set to restart on exit.

1b. Hand the server to an agent

This gets the remaining piece — real start, stop and restart, plus SteamCMD updates from the UI — by putting a sidecar agent in charge of the game process. What happens next depends on which machine you are on.

On Linux: keep the install, change what runs it

The agent can adopt your existing install directory as-is. It runs the game as a child process inside its container while the files stay on your disk, so nothing is downloaded again.

  1. Stop the bare-metal server, and disable the service if you made one — two things must never run the same install at once.
  2. Check ownership. The container runs as a user you choose; that user must own the install directory. sudo chown -R 1000:1000 /home/you/palworld, matching whatever you set below.
  3. Run the agent against that directory:
    docker-compose.yml — agent over an existing install
    services:
  palagent:
    image: ghcr.io/safwyls/palagent:latest
    user: "1000:1000"
    ports:
      - "8811:8811"       # the console reaches the agent here
      - "8211:8211/udp"   # the game, on the ports players already use
      - "8212:8212"
      - "25575:25575"
    environment:
      PALAGENT_MODE: supervisor
      PALAGENT_TOKEN: <openssl rand -hex 24>
      PALAGENT_ADMIN_PASSWORD: <your existing admin password>
    volumes:
      # Your existing install, exactly where it already is.
      - /home/you/palworld:/palworld
    restart: unless-stopped
  4. Register it in the console with the agent URL http://<host>:8811 and that token — or let the console discover and adopt it, which recovers both for you.

The agent should start the game within seconds. If SteamCMD begins downloading several gigabytes, it did not recognise the install — check the volume really points at the directory containing PalServer.sh, and that the container's user can write there.

On Windows: move the world, not the install

A Windows install cannot be supervised by a Linux container — the agent would fetch the Linux build over the top of it. Bring the world across instead; save files are portable between the two, which is why this works at all.

  1. Stop the Windows server and copy its world directory somewhere safe.
  2. Raise a fresh server from the console's wizard, on the machine that will host it, reusing the same published ports and admin password. Let it install and start once, so the directory structure exists.
  3. Stop that new server from the console.
  4. Copy your world into the new install — see the table below for where — replacing what the fresh install created, and match the ownership of the surrounding files.
  5. Start it, and join to confirm your world is the one that loaded.

Enshrouded is Windows-only as a server binary and the agent already runs it under Wine, so a Windows-hosted Enshrouded world moves the same way.

Where each game keeps its world

Relative to the install directory:

GameWorld lives at
PalworldPal/Saved/SaveGames/0/<world-id>/ — the folder holding Level.sav
DragonwildsRSDragonwilds/Saved/SaveGames/ — the .sav files
Enshroudedsavegame/ — extensionless blobs plus their -index and -info sidecars

Copy whole directories, sidecars included. A world is more than its biggest file.

Route 2 — Adopt it

If the server already runs one of our agent images, this is the entire migration. The console finds the container, recovers its token, admin password, server name and ports, and writes the row itself — no downtime and nothing typed.

Press + in the server rail; claimable containers appear at the top. Two conditions have to hold, and each fails with its own message:

  • The agent port must be published, or there is no address to reach it on.
  • Anvil must know this console's envPrefix, or it returns no environment and there is no token to recover — see Anvil.

Route 3 — From another container setup

A community game-server image, or your own compose file. Two options, and the first is the same five-minute move as 1a: point a console at it, mounting the world and config directories from wherever that container keeps them, and set DOCKER_HOST at a socket proxy so power control works through Docker.

For the full set of features, replace the container with a provisioned one wrapped around your existing world:

  1. Snapshot, then stop and remove the old container. Its world is on a host path and survives; confirm it is a bind mount and not a named volume before removing anything.
  2. Move the world to <that console's dataRoot>/<slug>. Anvil always places data there and the slug comes from the server name you type, so pick a name whose slug matches the directory — "Fluffy" means <dataRoot>/fluffy.
  3. chown it to the user the new container will run as.
  4. Raise it from the wizard with the same ports and admin password, and a matching Run as.

If SteamCMD starts downloading, stop. The install is not where the slug expects it. Nothing is lost yet — fix the path before letting it write.

Why replace the container instead of relabelling it? Anvil can only recreate or destroy containers it made. One deployed by hand has another orchestrator that would fight it, so letting Anvil build the container is what makes it manageable.

Route 4 — Retire a legacy provisioner

Older palcon deployments ran an agent in provisioner mode: one container that placed the others. That role is Anvil's now, and the console no longer reads PROVISIONER_URL/PROVISIONER_TOKEN.

  1. Stand up Anvil — Running it — with a client entry for this console, including its envPrefix and a mounted data root.
  2. Swap the console's environment: ANVIL_URL and ANVIL_TOKEN in, the old pair out. Setting only the old pair logs a warning and leaves the wizard absent — the two speak different protocols, so the old URL cannot be reused.
  3. Existing game servers are untouched; bring them into the wizard with route 2.
  4. Remove the old provisioner container. It is not a game server, and adopting it is refused for that reason.

Keeping players' bookmarks

Reuse the same host and the same published game ports and nobody has to do anything — the server is at the address they already saved. Changing ports means everyone re-adds it, so it is worth some effort to keep them even when a wizard proposes different ones.

Rolling back

Until you have joined the migrated server and seen your world, keep the old setup stopped rather than deleted — the service disabled, the container stopped, the directory untouched. Rolling back is then starting it again. Once you are satisfied, remove the old one so two things never contend for the same ports or the same files.
