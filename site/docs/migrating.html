Migrate an existing server

You already have a server with a world people care about. Nothing here deletes that world, and every route can be rolled back — but take a snapshot first anyway, because the cheapest insurance is the one you didn't need.

Which route is yours

What you have nowRoute
It already runs one of our agent images (palagent, wkagent, flameagent)1 — Adopt it
It runs some other way and you want the dashboard today, with the least disruption2 — Register it by hand
You want the full thing: provisioning, file access, backups, supervised power3 — Re-raise it under Ilmari
You ran an older console with a provisioner-mode agent4 — Retire the legacy provisioner

Routes 2 and 3 are not exclusive. Registering by hand takes five minutes and gets the server on the dashboard now; you can do the full move later without losing anything.

Before you start

Whichever route, collect these four facts. Every one of them comes up later, and two of them are the difference between a migration that works and one that silently doesn't.

shell — replace with your container's name
# 1. Where the world actually lives, and 2. as which user it runs
docker inspect <container> --format \
  '{{.Config.User}}{{range .Mounts}}{{printf "\n%s %s -> %s" .Type .Source .Destination}}{{end}}'

# 3. Which ports it publishes — reuse these and nobody has to re-bookmark
docker port <container>

# 4. The admin password, if it was set through the environment
docker inspect <container> --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -i password

Check whether the world is on a bind mount (a host path) or a docker volume. A bind survives deleting the app; a named volume may not. If it is a volume, copy the data out to a host directory before you remove anything.

Then snapshot it. On TrueNAS a ZFS snapshot of the dataset is instant and free; anywhere else, cp -a the world directory somewhere off to one side.

Route 1 — Adopt it

The whole migration, if it applies. The console finds the container, recovers its token, admin password, server name and ports, and writes the row itself. Nothing to type and no downtime — the server keeps running throughout.

Press + in the server rail. Containers the console can claim appear at the top of the dialog; click Adopt.

Two conditions have to hold, and each fails with its own message:

  • The agent port must be published. Adoption needs an address to reach the agent on. If docker port showed no 8811, republish it — or use route 2 now and route 3 later.
  • Ilmari must know this console's environment namespace. That console's entry in ILMARI_CLIENTS needs its envPrefix, or Ilmari returns no environment and there is no token to recover. See Ilmari.

A container that does not appear at all is usually neither owned nor image-matched — check it runs one of our agent images, or that its image falls under that console's allowlist.

Route 2 — Register it by hand

Works with any server the console can reach over the network, however it was deployed. Press + → Add an existing server by hand and fill in the address and credentials.

You getYou don't
Live state, player list, metricsConfig editing
Moderation over the game's own protocolSave-backed views (pals, storage, world)
Power control, if DOCKER_HOST is setBackups
Scheduled restarts and alertsSteamCMD updates from the UI

The right-hand column is everything that needs file access. To get it without a full move, point the server's save path at a bind mount of the world directory, or deploy an agent alongside the game in companion mode — see Sidecar agents.

Route 3 — Re-raise it under Ilmari

This ends with a supervised, Ilmari-managed server with every feature working, wrapped around the world you already have. It is a container replacement, not a world migration: the world never moves between machines, only into the directory the platform expects.

Why re-raise instead of relabel? Ilmari can only recreate or destroy containers it made. One deployed by hand — a TrueNAS app, your own compose file — has another orchestrator that would fight it. Letting Ilmari build the container is what makes it manageable.

The one rule that decides everything

Ilmari always places data at <that console's dataRoot>/<slug>, and the slug comes from the server name you type. So pick a name whose slug matches the directory you are going to put the world in — name it "Fluffy" and the directory is <dataRoot>/fluffy.

Steps

  1. Snapshot, per the section above.
  2. Stop and remove the old stack. Its world is on a host path and survives; the container is what has to go, so its ports are free and nothing else is writing the world. Removing a TrueNAS app does not touch a host-path mount.
  3. Move the world into place. If the old server was run by our agent, the data directory is already the full game install — move the whole thing:
    shell
    mv /old/path/fluffy /mnt/tank/apps/palcon-servers/fluffy
    If it was someone else's image, its layout probably differs. Let the agent install the game fresh in step 5, stop it, then copy just your world in — see the table below.
  4. Fix ownership to the user the new container will run as:
    shell
    sudo chown -R 568:568 /mnt/tank/apps/palcon-servers/fluffy
  5. Raise it from the wizard. Use the name whose slug matches the directory, the same published ports as before, the same admin password (paste it under Advanced, or players and admins get a new one), and a Run as matching step 4.
  6. Watch the first boot. The agent should find the install already present and start in seconds.
  7. Delete the old row if you had registered the server by hand.

If SteamCMD starts downloading several gigabytes, stop. That means the agent did not find your install where the slug expects it — the directory name and the server's slug disagree, or the move landed somewhere else. Nothing is lost, but fix the path before letting it write.

Where each game keeps its world

Relative to the install directory, if you are copying a world into a fresh install rather than moving a whole one:

GameWorld lives at
PalworldPal/Saved/SaveGames/0/<world-id>/ — the folder holding Level.sav
DragonwildsRSDragonwilds/Saved/SaveGames/ — .sav files
Enshroudedsavegame/ — extensionless blobs plus their -index/-info sidecars

Copy the whole directory, sidecars included, and match the ownership of everything around it.

Keeping players' bookmarks

Reuse the same host and the same published game ports and nobody has to do anything — the server is at the address they already saved. Changing ports means everyone re-adds it, so it is worth some effort to keep them, even if the wizard proposes different ones.

Route 4 — Retire a legacy provisioner

Older palcon deployments ran an agent in provisioner mode: one container that placed the others. That role is Ilmari's now, and the console no longer reads PROVISIONER_URL/PROVISIONER_TOKEN.

  1. Stand up Ilmari — Running it — with a client entry for this console, including its envPrefix and a mounted data root.
  2. Swap the console's environment: ILMARI_URL and ILMARI_TOKEN in, PROVISIONER_URL and PROVISIONER_TOKEN out. Setting only the old pair logs a warning and leaves the wizard absent — the two speak different protocols, so the old URL cannot be reused.
  3. Your existing game servers are untouched: their agent containers keep running with the same environment. Bring them into the wizard with route 1.
  4. Remove the old provisioner container. It is not a game server, and adopting it is refused for that reason.

Rolling back

Until you have joined the migrated server and seen your world, keep the old stack stopped rather than deleted. Rolling back is then starting it again and pointing the console back at it. Once you are satisfied, delete the old stack so two things never contend for the same ports or the same directory.
